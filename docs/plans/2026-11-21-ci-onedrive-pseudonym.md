**Goal:** ไฟล์ CI จากจังหวัด (ทุกสาขาในไฟล์เดียว) ถูกแยกเป็นซองล็อกต่อสาขา วางบน OneDrive ธนาคาร → เฉพาะเครื่องที่ผ่านการขออนุญาตและแอดมินอนุมัติเท่านั้นถอดได้ เห็นข้อมูลเฉพาะสาขาตัวเอง → เซิร์ฟเวอร์ไม่มี CIF/ชื่อ/ยอดหนี้ (มีแค่รหัสสุ่ม + พิกัด)

**Architecture:** หน้าเว็บแอดมินอ่าน CI ในเบราว์เซอร์ หารหัสสุ่มด้วยความลับที่อยู่ในเครื่องแอดมิน แล้วเข้ารหัสแยกซองต่อสาขา → แอดมินลากซองเข้า OneDrive (ไม่ใช้ Graph API) → แอปแท็บเล็ตสแกน QR ครั้งเดียว ขออนุญาต รออนุมัติ แล้วโหลดเฉพาะซองสาขาตัวเอง → ถอดใน RAM เก็บตารางแปลง "รหัส↔CIF" ไว้ในเครื่อง → join กับพิกัดที่เซิร์ฟเวอร์ส่งมาโดยเซิร์ฟเวอร์ไม่รู้ว่าคือใคร

**Tech Stack:** Web Crypto (AES-256-GCM + HMAC), vanilla JS, IndexedDB, OneDrive sync, Cloudflare D1/Pages Functions

---

## 1. กฎเหล็ก (ห้ามฝ่าฝืน)

1. ความลับสำหรับทำรหัสสุ่ม (HMAC secret) อยู่ในไฟล์ที่แอดมินเลือกจากเครื่องตอนใช้งาน — **ไม่ฝังในโค้ดเว็บ / ไม่ขึ้นเซิร์ฟเวอร์**
2. CIF / ชื่อ / ยอดหนี้ **ไม่ถูกส่งขึ้นเซิร์ฟเวอร์** ในการใช้งานปกติ
3. สิ่งที่เซิร์ฟเวอร์ได้คือ `{code, lat, lng, branch}` เท่านั้น
4. รหัสต้องคงที่: CIF เดิม → รหัสเดิมทุกครั้งที่อัป CI ใหม่ (ไม่งั้นหมุดกับชื่อเพี้ยน)
5. หน้านำเข้า CI ต้องอยู่หลัง PIN และจำกัดเฉพาะ admin กลาง
6. สคริปต์ที่แตะเลขจริง (จำนวนแถว/ยอดหนี้) ทิ้ง 1 `assert` self-check พอ ไม่ทำ framework เทสต์

## 3. ภาพการทำงาน (mockup — ยังไม่เขียนโค้ด)

```
[แอดมินกลาง] ไฟล์ CI ทั้งจังหวัด
   → เปิดในหน้าเว็บ (อ่านในเบราว์เซอร์)
   → แยกตามรหัสสาขา (145 / 854 / ...)
   → HMAC(CIF + ความลับในเครื่อง) = A7F3
   → เข้ารหัสเป็น "ซองต่อสาขา" + manifest (เวอร์ชัน/สาขา)
   → โหลด → ลากเข้าโฟลเดอร์ OneDrive        ← 4a

[ผู้ใช้] สแกน QR ครั้งเดียว
   → กรอก ชื่อ/สาขา/ตำแหน่ง/รหัสพนักงาน/ยืนยันเครื่อง
   → รออนุมัติ → branch_admin ตรวจ → กดอนุมัติ
   → แอปเจอสถานะ → ได้กุญแจสาขา → โหลดเฉพาะซองสาขาตัวเอง
   → ถอดใน RAM → เก็บตาราง A7F3↔CIF ในเครื่อง → ลบซอง

[ใช้งาน] เซิร์ฟเวอร์ส่ง {A7F3,lat,lng} → เครื่อง join → 📍 นายสมชาย (25,000)
          เครื่องที่ไม่ได้รับอนุมัติ → เห็นจุด แต่ไม่มีชื่อ
```

## 4. เฟสงาน (ลำดับบังคับ ห้ามข้าม)

### Phase 0 — Preflight + สำรอง (read-only, ~0.5 วัน)
- ไฟล์: `scripts/preflight-ci.sh` (ใหม่), `backups/pre-ci-2026-11-21/` (ใหม่)
- ทำ: ยืนยัน baseline ด้านบนซ้ำ · นับ KV ด้วย `wrangler kv key list` · สำรอง D1 (`wrangler d1 export`) + KV + `customers-db.json` 3 ชั้น (เครื่อง / git / vault)
- ผลที่ต้องได้: รายงาน baseline + ไฟล์สำรองที่เปิดได้จริง
- เกณฑ์ผ่าน: จำนวนแถวตรงกันทั้ง 3 ชั้น; restore ทดลองได้ 1 ชุด
- ยังไม่แตะโค้ดแอป

### Phase 1 — หน้านำเข้า CI + แยกสาขา + ทำรหัส + เข้ารหัส (~2 วัน)
- ไฟล์: `public/ci-admin.html` (ใหม่), `public/js/ci-pack.js` (ใหม่)
- ทำ: เลือกไฟล์ CI → ตรวจรูปแบบ → เลือก secret file → HMAC → แยกตาม `COL_BRANCH` → AES-GCM → โหลด `.bfrpack` + `manifest.json`
- self-check: ทดสอบ CIF เดิมสองรอบได้รหัสเหมือนกัน (`assert`); ทดสอบซองสาขา 145 เปิดด้วยกุญแจ 854 ไม่ได้
- เกณฑ์ผ่าน: จำนวนแถวในซองรวม = จำนวนแถวไฟล์ต้นทาง; เปิดซองด้วยโปรแกรมอื่นแล้วอ่านไม่ได้
- ประตู: โชว์หน้าเว็บจริงให้พ่อดูก่อน deploy

### Phase 2 — ขออนุญาต + อนุมัติ (~1.5 วัน)
- ไฟล์: `public/enroll.html` (ใหม่), `functions/api/enroll.js` (ใหม่), ใช้ `functions/api/staff.js` ที่มีอยู่
- ทำ: สแกน QR → ฟอร์ม 5 ข้อ → สถานะ `pending/approved/rejected` → หน้าอนุมัติของ branch_admin
- ใช้สิทธิ์ 3 ชั้นเดิม: admin กลาง / branch_admin สาขา / user
- ข้อมูลที่ขึ้นเซิร์ฟเวอร์: ชื่อเจ้าหน้าที่ + สาขา + รหัสเครื่อง (ไม่ใช่ข้อมูลลูกค้า)
- เกณฑ์ผ่าน: เครื่องที่ยังไม่ approve โหลดซองไม่ได้

### Phase 3 — ฝั่งแท็บเล็ต: ถอดซอง + join ในเครื่อง (~1.5 วัน)
- ไฟล์: `public/js/pseudonym.js` (ใหม่), แก้ `public/js/storage.js`, `public/js/customers.js`
- ทำ: ตรวจ manifest เทียบสาขาบัญชี → ถอดใน RAM → เก็บตาราง `code↔CIF` ใน IndexedDB (encrypted) → ลบซอง → join กับพิกัดตอน render
- เกณฑ์ผ่าน: เปลี่ยน CIF ในซอง → ชื่อในหน้าแผนที่เปลี่ยนตาม; ซองข้ามสาขาเข้าเครื่องไม่ได้
- **วิธีนำเข้าฝั่งผู้ใช้: ปุ่มเดียวในแอป — ดู §14 (พ่อกำหนด 21 พ.ย. 69)**

### Phase 4 — ย้าย CIF → รหัสสุ่มบนเซิร์ฟเวอร์ (~1 วัน, เสี่ยงสุด)
- ไฟล์: `scripts/migrate-cif-to-code.py` (ใหม่)
- ทำ: dry-run ก่อน → แปลง `customers` 11,810 แถว + `gps_history` 810 แถว → ตรวจว่าไม่มี CIF เหลือ
- หมายเหตุ: ระหว่าง migrate CIF ถูกใช้นิยามใน WHERE (ส่งไปชั่วคราว) แต่ไม่ถูกเก็บเพิ่ม
- rollback: `wrangler d1 export` จาก Phase 0 → restore; ประเมิน ~10 นาที
- ประตู: **ต้องให้พ่ออนุมัติหลังเห็น dry-run** ก่อนรันจริง

### Phase 5 — นำร่อง 1 สาขา (~1 วัน)
- วังท่าช้าง 854 ก่อน → ทดสอบ 3 คนทำเองได้ → ประเมิน → ค่อยขยาย 145

## 5. ประตูอนุมัติ (approval gates)

1. พ่ออนุมัติแผนนี้ → ค่อยเริ่ม Phase 1
2. โชว์ภาพหน้าเว็บจริงก่อน deploy (กติกาเดิม: งานเว็บต้องเห็นภาพก่อน)
3. โชว์ dry-run ของ Phase 4 ก่อน migrate จริง
4. แจ้งพ่อก่อน deploy ทุกครั้ง

## 6. Definition of Done

- จำนวนแถวในซองตรงต้นทาง 100% (มี assert)
- เปิด `.bfrpack` ด้วยโปรแกรมอื่น → อ่านไม่ได้
- ไม่มี CIF/ชื่อ/ยอดหนี้เหลือบนเซิร์ฟเวอร์ (ตรวจด้วย D1 query จริง)
- เครื่องไม่ได้รับอนุมัติ เห็นหมุดแต่ไม่เห็นชื่อ
- ออกจากระบบ → ล้างตารางแปลงในเครื่อง
- เน็ตหลุดหลังนำเข้า → ยังเปิดดูได้

## 7. ช่องว่างที่พบจากการประเมินแผน (21 พ.ย. 69 — คะแนนแผน 7.4/10)

3. **§7.3 (สูง) ความยาวรหัส** — ตัวอย่าง `A7F3` (4 ตัว) เสี่ยงชนกับ 11,810 ราย → บังคับ hex ≥10 ตัวอักษร (≥40 bit)
4. **§7.4 (สูง) deploy window** — ชน GitHub Action 05:05 ราคาน้ำมัน → กำหนด deploy เฉพาะ 09:00-16:00 + commit+push main ทุกครั้ง (ตามรูลเดิม)

## 8. คำตอบพ่อ (21 พ.ย. 69 — ครบแล้ว)

1. **ฟอร์ม 5 ข้อ**: รหัสพนักงาน · ชื่อ-สกุล · ตำแหน่ง · สาขา · จังหวัด
2. **ผู้อนุมัติ**: **แอดมินสาขา (branch_admin)** ก่อน — จังหวัดยังไม่เผยแพร่ จึงยังไม่ต้องมีชั้นอนุมัติกลาง
3. **สาขาต่อจังหวัด**: แต่ละจังหวัดมีจำนวนสาขาไม่เท่ากัน → หน้า CI admin ต้องรับรายการสาขาแบบ dynamic (ไม่ hardcode 145/854); ใช้ `COL_BRANCH` จริงในไฟล์เป็นตัวแบ่ง
4. **การลบซอง** (เสนอ 21 พ.ย. 69 — รอพ่อเคาะ):
   - แท็บเล็ต: ลบซอง + ไฟล์ชั่วคราวทันทีหลัง import สำเร็จ (ผ่าน checksum ก่อน)
   - OneDrive: เก็บเฉพาะซองเวอร์ชันล่าสุด 1 ชุด; มีเวอร์ชันใหม่ทับทันที
   - สำรอง: ซองเก่าเก็บใน `_retired/` ไม่เกิน 7 วัน แล้วลบ
5. **วันเริ่ม**: 21 พ.ย. 69 (วันนี้) — เริ่ม Phase 0

## 10. ปรับขอบเขต: เริ่มจากระดับสาขา (พ่อกำหนด 21 พ.ย. 69)

เหตุผล: ไฟล์ CI ระดับจังหวัดต้องให้ผู้บริหารส่งให้ ซึ่งไม่สะดวก → เริ่มที่ **ไฟล์ต่อสาขา** ก่อน แล้วค่อยขยายเป็นจังหวัดภายหลัง

สิ่งที่เปลี่ยน:
- **ไม่ต้องแยกสาขาในเว็บ** — ไฟล์ที่อัปเข้ามาเป็นของสาขาเดียวอยู่แล้ว (ตัดงาน split ออก)
- **คนอัป = branch_admin ของสาขานั้น** (ตรงกับคนอนุมัติที่พ่อเลือก)
- โฟลเดอร์ OneDrive แยกโฟลเดอร์ย่อยต่อสาขา → เครื่องอ่านเฉพาะโฟลเดอร์สาขาตัวเอง (แยกขาดกว่ารุ่นแรก)

```
BAAC-CI\
├── 854\
│   ├── manifest.json
│   └── 854-v2026-11-21.bfrpack
├── 145\
│   ├── manifest.json
│   └── 145-v2026-11-21.bfrpack
└── _retired\
```

มาตรการกันพลาด (เพิ่มจากเดิม):
- ตรวจ `COL_BRANCH` ของไฟล์กับสาขาของคนที่ล็อกอิน → ไม่ตรงให้ปฏิเสธ (กันอัปไฟล์สาขาอื่น)
- เตือนถ้าไฟล์มีหลายสาขาปนกัน (กรณีได้ไฟล์จังหวัดมา)
- ขั้นตอน export ไฟล์ CI ของสาขาเอง ต้องเขียนเป็นใบแนะนำ 1 หน้า (รอพ่อบอกเมนู/ขั้นตอนจริง)

ผลต่อแผนเวลา: ลดงาน split ออก ~0.5 วัน แต่เพิ่มงานตรวจสิทธิ์+ใบแนะนำ ~0.5 วัน → สุทธิเท่าเดิม [ประมาณการ]

## 11. การส่งซองขึ้น OneDrive — ลิงก์เดียว (พ่อกำหนด 21 พ.ย. 69)

พ่อจะสร้าง **ลิงก์ OneDrive 1 ลิงก์** ที่ทุกสาขาคลิกเข้าไปแล้วอัปโหลดซองได้ และเปิดดูได้ด้วย

กติกาที่ผูกกับลิงก์นี้:
1. **ชื่อไฟล์ต้องคงที่ ไม่ใส่วันที่** — `854.bfrpack`, `145.bfrpack`, … (เวอร์ชันเก็บไว้ในหัวไฟล์) เพื่อให้แท็บเล็ตโหลดชื่อเดิมได้ทุกครั้งโดยไม่ต้อง list ไฟล์
2. หน้า CI admin จบที่ 2 ปุ่ม: ดาวน์โหลดซอง → เปิดลิงก์เพื่ออัปโหลด (ไม่ต้องบอกเส้นทางโฟลเดอร์)
3. แท็บเล็ตอ่านจากลิงก์เดียวกัน: ระบุโฟลเดอร์ด้วย share token → หาไฟล์ `<สาขา>.bfrpack` → เทียบเวอร์ชันในหัวไฟล์ → ถ้าใหม่กว่า import แล้วลบ
4. ลิงก์ถูกเก็บครั้งเดียวตอนขออนุญาต (ฝังใน QR/ค่าตั้งของสาขา) — ไม่ต้องกรอกซ้ำ

**ต้องทดสอบวันจันทร์ (15 นาที)**: เอาไฟล์ตัวอย่างใส่โฟลเดอร์จริง → เปิดลิงก์ในเบราว์เซอร์แบบไม่ล็อกอิน → ยืนยันว่า list + ดาวน์โหลดได้ ถ้าไอทีบล็อกการแชร์แบบไม่ล็อกอิน ต้อง fallback เป็น: พ่อกด "publish" ที่คอม (คัดลอกซองไปโฟลเดอร์อ่านอย่างเดียว + เขียน `version.json`)

**ความเสี่ยงที่เหลือ**: ถ้าโฟลเดอร์เดียวเก็บซองทุกสาขา ผู้ที่เปิดดูได้จะเห็น *ชื่อไฟล์* ของทุกสาขา (อ่านข้อมูลไม่ได้เพราะเข้ารหัส) — ยอมรับได้ถ้าไฟล์แยกตามชื่อสาขาชัดเจน

## 14. การนำเข้าซองฝั่งแท็บเล็ต — ปุ่มเดียว (พ่อกำหนด 21 พ.ย. 69 — จำไว้เลย)

**หลักการ: ไม่ทำหน้า "นำเข้าข้อมูล" แยกต่างหาก** — พนักงานไม่เลือกไฟล์ CI (นั่นเป็นงานฝ่ายแอดมิน) และไม่ต้องมีขั้นตอนนำเข้าแบบแยกหน้า

### ทางที่เลือก (1 จิ้มจบ)

- หลังเครื่องได้รับอนุมัติ → แอปมีปุ่ม **"อัปเดตข้อมูลสาขา"** เพียงปุ่มเดียว
- กดปุ่ม → แอปโหลดซอง `<branch>.bfrpack` จากลิงก์ OneDrive เดียวกันเอง (§11) → เทียบเวอร์ชันในหัวซอง → ไขใน RAM → เก็บตาราง `code↔CIF` ลง IndexedDB (encrypted) → ลบซองทันที
- **กดซ้ำปลอดภัย**: ถ้าเวอร์ชันเดิมอยู่แล้ว แจ้ง "เป็นปัจจุบันแล้ว" ไม่ import ซ้ำ
- ตอน render: เซิร์ฟเวอร์ส่งแค่ `{code, lat, lng, branch}` → เครื่อง join กับตารางในเครื่อง → โชว์ชื่อ
- ข้อมูลที่วิ่งเข้าเครื่องคือซองที่เข้ารหัสแล้ว เซิร์ฟเวอร์ไม่เคยเห็นชื่อ/CIF/ยอดหนี้

### ทางสำรอง (ถ้า OneDrive ไม่ยอมให้เว็บอื่นโหลด — ทดสอบวันจันทร์)

ยังอยู่หน้าเดิม ไม่เพิ่มหน้าใหม่ — เปลี่ยนจาก 1 จิ้มเป็น 3 จิ้ม:
1. กด "เปิดลิงก์ OneDrive" → 2. โหลดไฟล์ซอง → 3. กลับแอปกด "เลือกไฟล์ซอง"

สาเหตุที่ต้องเทสต์: OneDrive อาจไม่ส่ง CORS header สำหรับ `fetch()` จาก origin อื่น หรือบังคับล็อกอิน → ถ้าไอทีบล็อก anonymous ให้ใช้ fallback publish ตาม §11

### ช่องว่างที่ยังต้องตัดสินใจ (ถามวันจันทร์)

- **กุญแจสาขาไปถึงแท็บเล็ตตอนอนุมัติยังไง**: ฝังใน QR ที่หัวหน้าสาขาแสดง (อายุสั้น/ใช้ครั้งเดียว) หรือให้แอปขอผ่าน API หลังสถานะเป็น approved — ยังไม่เลือก
- ห้ามเก็บ master secret บนเซิร์ฟเวอร์ (กฎเหล็ก §1.1) ทุกทางต้องรักษากฎนี้

### เกณฑ์ผ่านของทางเลือกนี้

- พนักงานจิ้มไม่เกิน 1 ครั้ง (ปกติ) หรือ 3 ครั้ง (fallback) นับตั้งแต่เปิดแอปจนเห็นชื่อลูกค้า
- ไม่มีหน้า "เลือกไฟล์ / นำเข้า / ตารางประมวลผล" โชว์ในกรณีปกติ
- กดปุ่มซ้ำ 2 ครั้ง → ตารางในเครื่องไม่ซ้ำกัน (idempotent)
- หลัง import สำเร็จ → ไม่มีไฟล์ `.bfrpack` ค้างในเครื่อง
