## 1. บทสรุปผู้บริหาร

วันนี้แอป “อ่านออฟไลน์ได้” และ “เขียนในเครื่องได้บางส่วน” แต่ยังไม่ใช่ offline-first จริง เพราะ:

- ทุกครั้งที่แก้ลูกค้า 1 ราย ระบบเขียน **รายชื่อทั้งก้อน ~3.9 MB** ลง IndexedDB ใหม่ทั้งชุด → แท็บเล็ตหน่วง และรูปถ่ายยิ่งทำให้หนัก
- งานที่แก้ตอนออฟไลน์ถูกจำด้วย **ชุด CIF (dirty set)** ไม่มี “คิวงาน” จริง → ไม่รู้ว่าอะไรส่งแล้ว/ยังไม่ส่ง, ส่งซ้ำได้, และชนกันแล้วไม่มีใครบอก
- ประวัติเยี่ยม (visits) เก็บใน **localStorage** (เพดาน ~5 MB) → โตขึ้นเรื่อย ๆ และหายได้เมื่อระบบเคลียร์พื้นที่
- ไม่มี `navigator.storage.persist()` → Android/iOS อาจลบข้อมูลในเครื่องเมื่อพื้นที่ต่ำ
- แผนที่ออฟไลน์มีเฉพาะไทล์ที่เคยเปิด (cache จำกัด 500 ไทล์)

**ข้อเสนอ:** ยกเครื่องเฉพาะ “ชั้นข้อมูล” (ไม่แตะ UI/flow ที่ใช้อยู่) เป็นสถาปัตยกรรม **Local-first + Outbox + Idempotent sync** ใช้เวลา MVP 4 วัน / สมบูรณ์ 10 วัน (เดิมประเมิน 3/9 — ตรวจโค้ดจริงพบงาน build `vendor.js` + SW precache ที่ต้องแก้ก่อน ~1 วัน)

> **ทิศทางล่าสุด 11 พ.ย. 69:** ข้อมูลลูกค้าเป็น **local-only** — แยก master/activity, ทุกเครื่องในสาขาใช้ CI ชุดเดียวกัน, ซิงก์เฉพาะ activity ในสาขา, แอดมิน 1 ท่านต่อสาขา (รายละเอียดข้อ 5.1)
>
> **เลือกแล้ว 11 พ.ย. 69:** **แบบ 1 — Auto Cloud Vault (E2E)** · ซิงก์อัตโนมัติ ไม่มีฮาร์ดแวร์ · ข้อมูลออกเน็ตแบบเข้ารหัส (รายละเอียดข้อ 5.3) · แบบ 2/3 เป็น fallback

## 2. นิยามระดับ offline (L0–L4)

| ระดับ | ความหมาย | สภาพวันนี้ |
|---|---|---|
| **L0** | เปิดแอปได้ตอนเน็ตหลุด แต่ไม่มีข้อมูล | ผ่าน (Service Worker แคช app shell) |
| **L1** | อ่านข้อมูลลูกค้า/หนี้ได้ตอนออฟไลน์ | ผ่าน (IndexedDB + Cache API) |
| **L2** | เขียนในเครื่องได้ แล้วรอส่ง | **ผ่านบางส่วน** — dirty set ไม่มีคิว/ไม่มีสถานะ |
| **L3** | คิวส่งเชื่อมิดชัด (outbox) ส่งซ้ำไม่เกิดข้อมูลซ้ำ มี conflict log | ❌ ยังไม่มี |
| **L4** | ภาคสนามเต็มรูปแบบ: แผนที่โหลดล่วงหน้า, รูป, รายงาน, หลายวัน, quota | ❌ ยังไม่มี |

**เป้าหมายแผนนี้ = L3** + บางส่วนของ L4 (รูปแยก store, storage health, แผนที่พร้อมใช้)

| งานค้าง | `bfr_dirty_cifs` = Set ของ CIF | ✅ | ไม่มีลำดับ/เวลา/จำนวนครั้ง/error, ไม่มี op id | `storage.js:129-162` |

| หนี้ (CI) | Cache API `bfr-debt-v1` เก็บ response ~3.3 MB | ✅ | ไม่มีอายุข้อมูล/สถานะแคชให้ผู้ใช้เห็น | `debt-db.js:16-40` |

## 5. สถาปัตยกรรมเป้าหมาย (L3)

### หลักการ
> **“เครื่องคือแหล่งความจริงของงานที่ยังไม่ส่ง; เซิร์ฟเวอร์คือแหล่งความจริงของงานที่ส่งแล้ว”**
> ทุกการเขียน = 1 รายการใน outbox พร้อม `opId` ไม่ซ้ำ → ส่งกี่ครั้งก็ได้ผลเท่าเดิม

```
[ผู้ใช้แก้ข้อมูล]
      │
      ▼
┌──────────────────────────────┐
│ IndexedDB v2 (transaction)   │
│  customers  (per record)     │
│  visits     (per user+cust)  │
│  photos     (blob แยก)       │
│  outbox     (opId, seq, ...) │
└──────────────┬───────────────┘
               │ วาด UI ทันที (ไม่รอเน็ต)
               ▼
        [drainOutbox()]
         ├─ offline → หยุด, ป้าย “รอส่ง N”
         └─ online  → POST /api/sync/ops (batch ≤50)
                        │
                        ▼
              D1: sync_ops(op_id UNIQUE) + customers
                        │
              ┌─────────┴─────────┐
              │ 200 ok             │ 409 conflict
              ▼                    ▼
        ลบ op ออกจากคิว      เก็บ server record + conflict log
```

### IndexedDB v2 schema
| Store | keyPath | Index | ใช้ทำอะไร |
|---|---|---|---|
| `customers` | `id` | `cif`, `branch`, `zone`, `updatedAt` | อ่าน/แก้รายคน ไม่ต้องเขียนทั้งก้อน |
| `visits` | `[user, customerId]` | `customerId`, `timestamp` | ย้ายออกจาก localStorage |
| `photos` | `customerId` | — | เก็บ Blob แยกจาก record |
| `outbox` | `seq` (auto) | `opId`, `status`, `entity` | คิวงานที่ยังไม่ส่ง |
| `meta` | `key` | — | lastPullAt, lastPushAt, clockOffset, schemaVersion |
| `kv` (เดิม) | `key` | — | เก็บไว้ช่วง migration/rollback |

### Outbox record
```js
{
  seq: 123,                     // ลำดับในเครื่อง
  opId: "dev7-1731234567890-12",// ไม่ซ้ำ (deviceId + ts + seq)
  entity: "customer",           // customer | visit | route
  key: "CIF0001234",
  patch: { note: "...", lat: 13.7 },  // เฉพาะฟิลด์ที่แก้
  baseUpdatedAt: "2026-11-11T...",    // เวอร์ชันที่ผู้ใช้เห็นตอนแก้
  createdAt: "...",             // เวลาเครื่อง
  createdAtServer: "...",       // เวลาเซิร์ฟเวอร์ (เติมตอนส่ง)
  tries: 0, lastError: null,
  status: "pending"             // pending | sending | failed | conflict
}
```

### จุดที่ต้องแก้ (ไฟล์)
| ไฟล์ | สิ่งที่ทำ |
|---|---|
| `public/js/storage.js` | IDB v2, migration, CRUD per-record, outbox, drain, conflict log |
| `public/js/api.js` | `POST /api/sync/ops`, backoff, `AbortController` timeout |
| `public/js/app.js` | ป้าย “รอส่ง N / ข้อมูล ณ วันที่”, online/visibility drain, persist() |
| `public/js/visit.js`, `calendar.js` | บันทึกผ่าน outbox (API เดิม `Storage.saveVisit`) |
| `public/sw.js` | ไม่แคช POST; คงแคชเฉพาะ GET; เพิ่มข้อความเตือน offline |
| `functions/api/sync.js` | รับ ops, ตรวจ `op_id` ซ้ำ, apply patch, คืน conflict |
| `functions/api/customers.js` | ใช้ conflict check เดียวกัน (ถ้ามี PUT ตรง) |
| D1 migration | ตาราง `sync_ops(op_id TEXT PRIMARY KEY, device_id, applied_at, result)` |

## 5.1 สถาปัตยกรรมหลายสาขา + Local-only (ทิศทางล่าสุด 11 พ.ย. 69)

> ข้อสรุปจากที่คุยกับพ่อ: **สาขา = 1 วงข้อมูลปิด** · ข้อมูลลูกค้าไม่ขึ้นคลาวด์ · ทุกเครื่องในสาขามี master ชุดเดียวกัน · ซิงก์เฉพาะ “งานที่ทำ” (activity) ไม่ส่งข้อมูลลูกค้าซ้ำ

### แยก 2 ชั้น

| ชั้น | เก็บอะไร | มาจากไหน | ซิงก์ไหม |
|---|---|---|---|
| **Master** | CIF, ชื่อ, ที่อยู่, หนี้, ชั้นหนี้ | ไฟล์ CI เข้ารหัส `.bfrpack` — ไฟล์เดียวกันทุกเครื่องในสาขา | ❌ ไม่ซิงก์ (โหลดใหม่เมื่อ CI เปลี่ยน) |
| **Activity** | พิกัด, ผลเยี่ยม, หมายเหตุ, วันนัด, ยอดรับปาก | เจ้าหน้าที่บันทึกหน้างาน | ✅ ซิงก์เฉพาะในสาขา |

### Activity payload (ไม่ส่งข้อมูลทะเบียนลูกค้า)
> ⚠️ แม้ไม่ส่งชื่อ/ที่อยู่/ยอดหนี้ แต่ **CIF + พิกัด + หมายเหตุ ยังเป็นข้อมูลส่วนบุคคล** → ต้องเข้ารหัสทั้งตอนส่งและตอนเก็บ
```json
{
  "opId": "wtc-tab3-1731234567890-12",
  "branchId": "WTC",
  "deviceId": "tab3",
  "ciVersion": "2026-11-09",
  "cif": "4600001",
  "type": "gps|visit|promise|note",
  "lat": 13.7, "lng": 101.9,
  "visitResult": "promised",
  "note": "...",
  "promiseDate": "2026-11-20",
  "promiseAmount": 5000,
  "createdAt": "2026-11-11T09:00:00+07:00",
  "createdAtServer": null
}
```
**ไม่ส่ง:** ชื่อ ที่อยู่ เบอร์ เลขบัตร ยอดหนี้ ข้อมูลสัญญา

### การไหลของข้อมูล
```
ไฟล์ CI (เข้ารหัส) ──► ทุกเครื่องในสาขา (master เดียวกัน)
เครื่อง A ─┐
เครื่อง B ─┼─ activity ops ──► Hub สาขา ──► เครื่องอื่นดึง ops ใหม่
เครื่อง C ─┘                         └──► backup ไฟล์เข้ารหัส (OneDrive ธนาคาร)
```

### บทบาทและสิทธิ์

| บทบาท | ทำอะไร | เห็นอะไร |
|---|---|---|
| **พ่อ (super admin)** | ตั้ง/ถอดแอดมินสาขา, ดูเวอร์ชัน/สถานะ | ไม่เห็นข้อมูลลูกค้า; เห็นสถิติรวมไม่ระบุตัวตน (ถ้าเปิด) |
| **แอดมินสาขา (branch_admin)** | นำเข้า CI, ตั้ง PIN, ดูแลเครื่อง, ออก backup/รายงาน | ข้อมูลลูกค้าในสาขาตัวเอง |
| **เจ้าหน้าที่** | เก็บพิกัด/บันทึกเยี่ยม | ข้อมูลลูกค้าในสาขาตามสิทธิ์ |

> ต้องเพิ่ม role `branch_admin` — ปัจจุบันระบบมีแค่ `admin` / `staff`

### ช่องทางซิงก์ในสาขา (ต้องเลือก)

| ทาง | ต้องมีอะไร | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **A — Hub 1 เครื่อง** | คอม/แท็บเล็ต 1 เครื่องรัน hub + Wi-Fi เดียวกัน | เร็ว, real-time, ข้อมูลอยู่ในสาขา | ต้องติดตั้ง/เปิดพอร์ต; PWA จาก LAN ต้อง HTTPS |
| **B — WebRTC peer-to-peer** | เบราว์เซอร์ + QR จับคู่ | ไม่ต้องติดตั้ง | Wi-Fi ธนาคารอาจบล็อก; เสถียรน้อย |
| **C — ไฟล์ activity เข้ารหัส** | OneDrive ธนาคาร | ทำได้แน่นอน, ไม่พึ่ง IT | ไม่ real-time; ต้องกดส่ง/รับเอง |

**แนะนำ: A + C** — hub เป็นหลัก, ไฟล์เข้ารหัสเป็น backup/fallback; ถ้า IT ไม่ให้ติดตั้ง → C อย่างเดียว

### สิ่งที่ศูนย์กลางเก็บได้ (ไม่ใช่ข้อมูลลูกค้า)
- โค้ดเว็บ + เวอร์ชัน
- รายชื่อสาขา + บัญชีเจ้าหน้าที่ (ชื่อ/บทบาท/สาขา) — ถ้าธนาคารอนุญาต
- ค่าตั้งระบบ/feature flags
- สถิติรวมไม่ระบุตัวตน (เช่น จำนวนเยี่ยมต่อสาขา)

### ข้อจำกัด / ความเสี่ยง
1. **พิกัดบ้าน + CIF ยังเป็นข้อมูลส่วนบุคคล** → ต้องเข้ารหัสทั้งตอนส่งและตอนเก็บ
2. **หมายเหตุ** อาจมีชื่อ/รายละเอียดลูกค้า → เตือน/จำกัด/เข้ารหัส
3. **Master ต้องเวอร์ชันตรงกัน** → activity แนบ `ciVersion`; เครื่องที่ CI เก่าต้องอัปเดตก่อน
4. **ลูกค้าใหม่** ที่ยังไม่มีใน master ของเครื่องอื่น → new-customer pack หรือให้แอดมินสาขาสร้าง
5. **ทุกเครื่องในสาขาหายพร้อมกัน** → ต้องมี backup เข้ารหัสนอกเครื่อง
6. **Wi-Fi ธนาคารอาจไม่ให้เครื่องคุยกัน** → ต้องทดสอบ/ขอ IT
7. **PWA จาก LAN ต้อง HTTPS** → ต้องมีใบรับรองหรือห่อเป็นแอป

### เวลาเพิ่มจากแผนหลัก
- **L1 — ไฟล์เข้ารหัส (C):** +2–3 วัน → รวม ~12–13 วัน
- **L2 — Hub ในสาขา (A+C):** +6–8 วัน → รวม ~16–18 วัน
- **L3 — เข้ารหัสแล้วซิงก์ผ่านเน็ต:** +4–5 วัน → รวม ~14–15 วัน (แต่มีความเสี่ยงเชิงนโยบาย)

### ยังต้องตัดสิน
1. ใช้ **hub (A)** หรือ **ไฟล์เข้ารหัส (C)** เป็นหลัก
2. ศูนย์กลางเก็บ **บัญชีเจ้าหน้าที่** ได้ไหม (ชื่อ/บทบาท/สาขา)
3. พ่อต้องการ **สถิติรวมข้ามสาขา** แบบไม่ระบุตัวตนไหม
4. **Backup นอกเครื่อง** เก็บ OneDrive ไหน (ส่วนตัว/ธนาคาร)

## 5.3 แบบ 1 — Auto Cloud Vault (E2E) — ทางที่เลือก

> เป้าหมาย: ผู้ใช้ไม่ต้องกดซิงก์ · ไม่มีฮาร์ดแวร์ในสาขา · ข้อมูลออกเน็ตแต่เป็น **ciphertext** · Cloudflare อ่านไม่ออก

### หลักการ
- เข้ารหัสที่เครื่องก่อนส่ง (WebCrypto AES-256-GCM)
- Cloudflare เก็บเฉพาะ `ciphertext` + metadata (branch, device, เวลา, ขนาด)
- กุญแจสาขา (Branch Key) อยู่ในเครื่องที่ได้รับอนุมัติเท่านั้น
- Sync อัตโนมัติเมื่อเปิดแอป / เน็ตกลับ / ทุก 60 วิ

### โครงกุญแจ (key hierarchy)
- **Branch Key (BK)** 256-bit สุ่มใหม่ต่อสาขา
- **Device Key (DK)** ต่อเครื่อง — ใช้ห่อ BK (envelope encryption)
- **QR จากแอดมินสาขา** = `branchId + BK (ห่อแล้ว) + API URL` — อายุ 15 นาที ใช้ครั้งเดียว
- **Device PIN** ใช้ปลดล็อก DK ในเครื่อง (PBKDF2/Argon2)
- **Rotate BK** เมื่อถอดเครื่อง/สงสัยรั่ว

### การไหล
```
เครื่อง A: activity → encrypt(BK) → outbox → POST /api/vault/ops
Cloudflare: D1/R2 เก็บ ciphertext (อ่านไม่ออก)
เครื่อง B: GET /api/vault/ops?since= → decrypt(BK) → apply
Master CI: encrypt(BK) → R2 → ทุกเครื่องโหลด/ถอด
```

### API
- `POST /api/vault/ops` — batch ≤50, idempotent ด้วย `opId`
- `GET /api/vault/ops?branch=&since=`
- `POST /api/vault/master` — admin only
- `GET /api/vault/master?branch=`
- `POST /api/vault/devices/pair` — QR token
- `GET /api/vault/health`

### Storage
- **D1:** `vault_ops`, `vault_devices`, `vault_branches`
- **R2:** master pack (~4 MB) ต่อสาขา/เวอร์ชัน
- **ห้ามเก็บ plaintext** และห้าม log payload

### สิ่งที่ต้องแก้ในแอป
- `VaultSync` แทน `Storage.push/pull`
- Crypto module (AES-GCM, PBKDF2, QR)
- ตัด `/api/debt-data` — master pack เป็นแหล่งข้อมูล
- Admin console สาขา + จัดการเครื่อง
- ป้ายสถานะ: ซิงก์แล้ว / รอส่ง N / master version

### ข้อควรระวังด้านความปลอดภัย
1. Cloudflare เห็น metadata — ถ้าธนาคารต้องการ “ไม่ออกนอกเลย” ต้องกลับไปแบบ 2/3
2. QR มีกุญแจ — ห้าม screenshot, หมดอายุ 15 นาที, ใช้ครั้งเดียว
3. PIN 4 หลักอ่อน — ใช้ 6 หลักหรือรหัสเครื่องในการปลดล็อกกุญแจ
4. XSS ขโมยกุญแจได้ — CSP + ไม่ใช้ JS บุคคลที่สาม + SRI
5. เครื่องหาย — rotate BK; เครื่องเก่ายังมีข้อมูลเก่า; ลบระยะไกลไม่ได้
6. กุญแจหาย = ข้อมูลกู้คืนไม่ได้ → ต้องมี key escrow ในตู้เซฟธนาคาร

### สิ่งที่ธนาคารต้องอนุมัติ
- อนุญาตให้ **ciphertext + metadata** อยู่บน Cloudflare
- อนุญาตให้เก็บกุญแจในเครื่อง (WebCrypto/IndexedDB)
- PDPA: ข้อมูลส่วนบุคคลที่เข้ารหัสยังเป็นข้อมูลส่วนบุคคล → ต้องมี DPA/บันทึกการประมวลผล
- แผนกู้คืนกุญแจ + แผนแจ้งเหตุ breach

### เฟสและเวลา (แบบ 1)
| เฟส | งาน | วัน |
|---|---|---|
| 0 / 0.5 / 0.7 | baseline, vendor, precache | 1.5 |
| 1 | IDB v2 + outbox | 1.5 |
| 2 | crypto + QR pairing | 2 |
| 3 | vault API + D1/R2 | 2 |
| 4 | master pack + versioning | 1 |
| 5 | admin console + backup | 1.5 |
| 6 | QA + pilot | 2 |
| buffer | | 1 |
| **รวม** | | **~13 วัน** |

### เริ่มทำ
1. เขียน crypto spec + threat model
2. Prototype: encrypt/decrypt + QR pairing บน 2 เครื่อง
3. Test: ปิดเน็ต → 30 ops → เปิด → sync 0 → ตรวจ D1 เห็นแต่ ciphertext
4. ขออนุมัติธนาคารก่อนขึ้น production

## 8. เกณฑ์ผ่านรวม (Definition of Done)

1. **ไม่หาย:** โหมดเครื่องบิน 2 ชม. ทำ 30 รายการ (แก้ 10 + ปักพิกัด 10 + เยี่ยม 10) → force close 3 ครั้ง → เปิดใหม่ครบ 30

4. **เร็ว:** แก้ 1 ราย ตอบสนอง UI ≤50 ms, IDB write ≤20 ms (วัดจาก baseline เฟส 0)
5. **ทนพื้นที่:** ใช้ <80% quota; ขอ persist สำเร็จ; มีป้ายเตือนเมื่อใกล้เต็ม

## 11. ทางเลือกให้พ่อเลือก

| ทาง | ขอบเขต | เวลา | ได้อะไร | เสียอะไร |
|---|---|---|---|---|
| **A — MVP (แนะนำ)** | เฟส 0–2 | **4 วัน** | งานออฟไลน์ไม่หาย, คิวชัด, ส่งซ้ำไม่พัง | แผนที่/รูปยังไม่เต็ม |
| **B — สมบูรณ์** | เฟส 0–5 | **10 วัน** | ภาคสนามเต็มรูปแบบ + แผนที่ + รูป + quota | ใช้เวลานาน, เสี่ยง migration |
| **C — เบา** | เพิ่มป้ายค้าง + persist + ซ่อม visits | **1 วัน** | รู้ว่าอะไรค้าง, ข้อมูลไม่ถูก evict | ยังเขียนทั้งก้อน, ยังไม่มี idempotency |

**คำแนะนำ: A ก่อน** แล้ววัดผล 1 สัปดาห์ ค่อยต่อ B — เพราะ A ปิดความเสี่ยง “ข้อมูลหาย” ได้ 80% ด้วยเวลา ~40% ของงานทั้งหมด

### 11.1 ตัวเลือกสถาปัตยกรรมข้อมูลหลายสาขา (ต่อจาก A/B/C)

| ทาง | ช่องทางซิงก์ activity | เวลาเพิ่ม | รวมกับแผนหลัก | เหมาะกับ |
|---|---|---|---|---|
| **L1 — ไฟล์เข้ารหัส** | OneDrive ธนาคาร | +2–3 วัน | ~12–13 วัน | IT ไม่ให้แตะเครื่อง/เน็ต |
| **L2 — Hub ในสาขา** | Wi-Fi ในสาขา + ไฟล์ backup | +6–8 วัน | ~16–18 วัน | IT อนุญาต + เครื่องเห็นกัน |
| **L3 — E2E ผ่านเน็ต (เลือกแล้ว)** | Cloudflare + เข้ารหัสก่อนส่ง | +3–4 วัน | ~13–14 วัน | อยาก real-time + ออโต้ |

> **เลือกแล้ว 11 พ.ย. 69: L3 — Auto Cloud Vault (E2E)** · L1/L2 เป็น fallback ถ้าธนาคารไม่อนุมัติ ciphertext บนคลาวด์

> ทั้ง 3 ทางใช้ **master/activity + branch_admin** เหมือนกัน ต่างกันแค่ช่องทางขน activity
> เดิมแนะนำ L1 ก่อน — **แต่พ่อเลือก L3 แล้ว** · ถ้าธนาคารไม่อนุมัติ ciphertext บนคลาวด์ ให้ถอยไป L1 (ไฟล์เข้ารหัส) ทันที

### คำถามที่ต้องตัดสินใจ (ตอบสั้น)
1. เริ่ม **A / B / C**?
2. `note` ชนกัน → **เก็บทั้งสอง (แนะนำ)** หรือ ใหม่ทับ?
3. แผนที่ออฟไลน์ (เฟส 4) เอาอยู่ในรอบนี้หรือรอบหน้า?
4. ~~สถาปัตยกรรมข้อมูลหลายสาขา~~ → **เลือก L3 (E2E cloud) แล้ว** — เหลือขออนุมัติธนาคาร; ถ้าไม่อนุมัติถอยไป L1
5. แอดมินสาขา → ใครเป็นคนตั้ง/ถอด (พ่อตั้งเอง หรือหัวหน้าเขตตั้ง)
